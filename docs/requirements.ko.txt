너는 모바일 캐주얼 게임의 리드 게임 개발자, 퍼즐 시스템 설계자, 테크니컬 아티스트, UI 디자이너, Cloudflare 백엔드 개발자 역할을 맡는다. 아래 명세에 따라 실제 플레이 가능한 iOS/Android 세로형 솔로 매치3 게임을 제작하라. 기획안이나 화면 목업만 제출하지 말고, 코드·게임 데이터·실제 이미지 에셋·서버·DB 마이그레이션·테스트·실행 문서까지 연결하라.

이 문서에서 지정한 자체 규칙이 참고 게임의 규칙보다 우선한다. 특히 하트는 원작과 달리 매판 시작할 때 소비한다. 작업을 내부 단계로 나누어 수행하되, 일상적인 구현 선택마다 질문하거나 첫 화면만 만든 뒤 종료하지 말라. 현재 저장소의 지침과 기존 코드를 먼저 확인하고, 관련 없는 코드를 덮어쓰지 말라. 구현 가능한 부분을 끝까지 진행하고, 외부 자격증명·도구 부재 때문에 검증하지 못한 항목만 마지막에 구체적으로 보고하라.

1. 제작 목표와 참고 범위

1.1 목표 경험
- Royal Match에서 참고할 것은 제한된 이동 횟수 안에 목표를 완수하는 매치3, 다양한 모양의 보드, 장애물, 특수 블록 조합, 경쾌한 연쇄 반응, 공간 복원, 매끄러운 모바일 조작이다.
- 퍼즐을 클리어하고 코인과 복원용 별을 얻은 뒤, 홈의 정원을 복원하고 다음 레벨로 진행하는 흐름을 만든다.
- 중심 콘텐츠는 솔로 매치3다. 길드는 하트·아이템 지원과 커뮤니티 기능을 제공한다. 실시간 협동 전투나 PvP를 추가하지 않는다.
- 참고 자료의 구출형 광고 장면을 본편으로 오해하지 않는다. 이번 범위에서는 매치3와 정원 복원에 집중한다.
- 첫 설치 후 로그인 요구 없이 게스트로 시작하고, 짧은 안내 후 첫 퍼즐을 직접 조작한다.

1.2 독자적인 결과물
- 개발 가칭: 구름정원 매치 / Cloud Garden Match. 출시 이름으로 확정하거나 상표 확인이 끝났다고 주장하지 않는다.
- 세계관: 구름 위의 정원과 온실, 분수 테라스, 작은 작업실을 복원한다.
- 마스코트: 청록색 작업복과 코랄색 목수건을 착용한 레서판다 정원사 루미. 둥근 머리, 짧은 팔다리, 호박색 눈, 크림색 볼, 줄무늬 꼬리, 새싹 모양 앞치마 주머니가 특징이다.
- 원작의 캐릭터·로고·음원·실제 이미지·정확한 UI 도안·레벨 데이터를 추출하거나 재사용하지 않는다. 스크린샷은 화면 구성과 완성도 분석에만 사용한다.
- 일반적인 캐주얼 게임의 시각 원리를 참고하되, 새로운 마스코트·타일 모양·프레임 장식·정원 구성·이벤트 아이콘을 제작한다.

2. 기술 구성

신규 프로젝트 기본 구성은 React + TypeScript + Vite + PixiJS + Capacitor다. 이미 유효한 프로젝트가 있다면 먼저 호환성을 검토하고, 불필요한 전체 재작성을 하지 않는다. 라이브러리는 실행 시점의 공식 문서와 호환성을 확인해 안정 버전으로 고정하고 lockfile을 남긴다.

- React: 앱 부팅, 화면 상태, 데이터 연결, 접근성, 실제 텍스트 입력과 계정·설정 흐름.
- PixiJS: 2D 이미지 스프라이트, 보드, 이미지 기반 게임 UI, AnimatedSprite, NineSliceSprite, 이미지 파티클.
- Capacitor: iOS/Android 패키징, 네이티브 로그인·스토어 결제·Google Mobile Ads 보상형 광고·보안 저장소·진동·앱 생명주기 연동.
- packages/game-core: 렌더링과 무관한 순수 TypeScript 결정론적 퍼즐 엔진. 클라이언트와 Workers가 같은 구현을 사용한다.
- Cloudflare Workers: 인증, 프로필, 게임 시작·행동 검증·결과 정산, 하트, 상점, 길드, 결제 검증, 광고 보상 intent와 SSV 검증 API.
- Cloudflare D1: 플레이어, 계정 연결, 재화, 인벤토리, 진행, 게임 세션, 지원 요청, 선물, 거래 원장.
- Cloudflare Durable Objects: 길드별 실시간 연결·채팅·지원 알림. 재화의 최종 권위 저장소는 D1 한 곳으로 유지한다.
- Cloudflare R2: 버전별 런타임 이미지, atlas, 콘텐츠 팩, 음원. 제작용 원본과 공개 런타임 에셋은 분리한다.
- Queues와 Cron은 콘텐츠 보충, 알림 재시도, 만료 처리 등 필요한 작업에만 사용한다. 초 단위 하트 회복 cron은 만들지 않고 요청 시 서버 시간으로 계산한다.
- 게임 서버·DB·스토리지는 Cloudflare를 사용한다. Google/Apple 로그인과 스토어 결제 자체는 각 공급자의 서비스를 정상적으로 연동한다.

권장 모듈: apps/client, apps/api, packages/game-core, packages/contracts, packages/content, packages/assets, tools/asset-pipeline, tools/level-validation, docs. 실제 저장소에 맞춰 이름은 조정해도 역할 분리는 유지한다.

3. 이미지 중심 구현 원칙

3.1 이미지로 제작할 것
배경, 캐릭터, 기본 타일, 특수 블록, 장애물, 보드 바닥, 보드 외곽과 코너, 버튼 외형, 그림자, 광택, 패널, 팝업 프레임, 리본, 재화 캡슐, 메뉴, 아이콘, 배지, 선택 강조, 튜토리얼 손가락, 말풍선, 폭발, 연기, 파편, 광선, 잔상, 반짝임, 보상 연출, 장면 전환 장식을 실제 래스터 이미지로 제작한다.

Three.js, 실시간 3D 모델, CSS gradient/border/box-shadow/clip-path, Pixi Graphics, Canvas 도형, SVG 도형, 셰이더, 이모지, 아이콘 폰트로 게임 미술을 대체하지 않는다. 엔진의 표준 텍스처 렌더링은 허용하며, 직접 만든 셰이더로 폭발·빛·프레임 외형을 생성하는 것은 허용하지 않는다.

3.2 코드가 담당할 것
- 이미지 배치, hit area, 스프라이트 이동·회전·균일 확대축소·투명도 보간, clipping/masking, atlas 재생, 9-slice 배치는 허용한다.
- 모든 파티클은 이미지 스프라이트다. 코드가 위치와 시간을 계산하고, 외형은 이미지가 담당한다.
- 위치·회전·크기·투명도만 달라지는 동작은 승인된 이미지 부품을 재사용한다. 형태 자체가 바뀌는 구간에 별도 프레임을 만들고, 단순 파편 이동까지 매번 새로운 이미지 생성으로 제작하지 않는다.
- 2D 렌더러를 사용한다는 이유로 도형 기반 임시 미술을 완성품으로 제출하지 않는다.
- CSS는 앱 컨테이너, safe area, 실제 입력 요소와 접근성 레이어 등 구조적인 용도로만 사용한다.
- 전체 화면 한 장에 클릭 영역만 얹지 않는다. 재사용 가능한 부품으로 나누고 상태·텍스트·터치 판정을 연결한다.

3.3 텍스트와 입력 예외
닉네임, 가격, 시간, 레벨 번호, 목표 수, 이동 횟수, 설명, 버튼 문구는 이미지에 구워 넣지 않고 런타임 텍스트로 표시한다. 숫자는 bitmap font atlas를 사용할 수 있다. 텍스트의 가독성을 위한 글꼴 테두리는 허용한다. 한글은 정상 글꼴로 표시하고 모든 한글을 대형 bitmap atlas에 무리하게 넣지 않는다. 닉네임·검색·채팅은 실제 입력 필드와 OS 키보드를 사용한다. Google/Apple 브랜드 버튼은 공급자의 공식 리소스와 표시 규칙을 따른다. 네이티브 로그인·결제·광고·개인정보 동의 화면은 해당 SDK의 정상 UI를 사용하며, 광고 영상과 광고 닫기 버튼을 자체 이미지로 재구현하거나 가리지 않는다.

4. 아트 방향과 모바일 레이아웃

4.1 아트 방향
- 밝고 풍성한 프리렌더 2.5D 캐주얼 게임 질감. 둥글고 도톰한 실루엣, 매끄러운 에나멜과 도색한 나무, 부드러운 그림자, 절제된 하이라이트.
- 같은 카메라 방향과 좌상단 광원을 유지한다. 타일과 아이콘은 작은 크기에서도 즉시 구분되어야 한다.
- 기본 팔레트: 깊은 청록 #126C81, 코랄 #FF7564, 따뜻한 크림 #FFF2D0, 플레이 버튼의 라임그린 #79C83F, 외곽 음영의 진한 남청 #1F3A54. 금색은 보상과 작은 테두리 포인트에만 쓴다.
- 웹 대시보드, 카드가 반복되는 SaaS 화면, 평면 머티리얼 버튼, 고대 양피지, 무거운 금속 갑옷, 과도한 황금 문양, 네온 테두리, 픽셀아트를 사용하지 않는다.
- 홈은 풍성한 정원 장면이고, 플레이 화면의 배경은 보드보다 조용하고 대비가 낮아야 한다.

4.2 반응형 기준
- 기준 논리 화면 390×844, 세로 우선. 360×800, 390×844, 430×932, 태블릿을 점검한다. 특정 기기의 실제 해상도라고 가정하지 않는다.
- 화면 전체를 강제로 늘이지 않는다. 배경은 지정된 crop safe area 안에서 cover, 캐릭터와 아이콘은 비율 유지, 프레임은 9-slice, 보드는 가용 공간에 맞춘다.
- 노치·홈 인디케이터·안드로이드 시스템 영역과 겹치지 않는다.
- 일반 버튼 터치 영역은 최소 44×44 논리 px를 목표로 한다. 보드 타일은 가장 작은 지원 화면에서도 약 36px 이상을 확보한다.
- 태블릿과 가로 화면에서는 보드 크기를 과하게 키우지 말고 중앙에 유지하고 주변 배경을 확장한다.
- 아이콘 투명 여백을 제외한 실제 시각 크기를 맞추고, 서로 다른 이미지의 baseline과 pivot을 맞춘다.

5. 필수 화면과 실제 동작

5.1 시작
스플래시 → 필수 리소스 확인과 게스트 세션 생성 → 첫 판. 로그인 모달과 여러 공지창을 먼저 띄우지 않는다. 자동 닉네임을 생성하고 설정에서 변경할 수 있게 한다.

5.2 홈
- 중앙은 복원 중인 정원 장면이며 웹 카드 목록으로 만들지 않는다.
- 상단: 프로필, 코인, 하트/무제한 남은 시간, 복원 별, 설정.
- 좌우 가장자리: 해금된 이벤트와 보상 아이콘을 소수만 배치한다. 초기에는 1~2개만 보이고 최대 4개를 기본으로 한다.
- 하단: 큰 다음 레벨 플레이 버튼, 지역 복원 진행/보상 버튼.
- 가장 아래: 이미지 아이콘을 사용하는 상점·홈·길드 메뉴. 퍼즐 플레이 중에는 홈 메뉴를 숨긴다.
- 4시간 무료 무제한은 받을 수 있을 때와 대기 중 상태가 구분된다.

5.3 레벨 시작 팝업
레벨 번호, 난이도, 목표, 시작 전 부스터 3종의 수량과 선택 상태, 시작 시 소모 하트 또는 무제한 표시, 플레이 버튼. 시작 전 부스터를 선택하는 시점에는 소비하지 않고 서버가 판 시작을 승인할 때만 소비한다.

5.4 퍼즐
- 상단 왼쪽 목표와 잔여 수, 중앙 작은 마스코트 반응, 오른쪽 크게 표시한 이동 횟수.
- 중앙 보드를 최대한 확보한다. 사각형뿐 아니라 계단·오목·구멍·분리형 보드도 실제 셀과 가장자리 이미지로 표현한다.
- 하단: 망치, 가로 쓸기, 세로 쓸기, 섞기와 수량. 작은 설정 버튼.
- 보드 위를 가리는 이벤트 광고, 배너, 결제 제안을 넣지 않는다.

5.5 결과
- 승리: 목표 완료 → 짧은 축하 이미지 연출 → 서버 검증된 기본 보상 지급 → 다음 레벨 또는 홈. 별도로 선택형 '광고 보고 코인 2배' 버튼을 제공하되 기본 보상 수령과 다음 레벨 이동은 광고 없이 가능해야 한다.
- 이동 횟수 소진: 모든 연쇄를 먼저 정산한 후 실패/이어하기를 판단한다.
- 이어하기: 추가 이동 +5와 정확한 코인 비용, 종료 버튼을 명확하게 표시한다. 이동 횟수 추가는 같은 판이며 하트를 다시 소비하지 않는다.
- 재도전: 새 판이므로 하트가 다시 필요하다.

5.6 하트 부족
현재 하트, 다음 자연 회복 시간, 무료 무제한 수령/대기, '광고 보고 하트 +1', 길드 요청, 보관된 하트 선물, 코인 충전 선택지를 보여준다. 하트가 없고 무제한도 없으면 새 판을 시작할 수 없다. 4시간 무료 무제한 수령에 광고 시청을 요구하지 않는다.

5.7 나머지 필수 화면
상점, 시즌 패스, 무료 보상, 정원 복원, 길드 찾기/생성/가입 승인/멤버/채팅/지원, 선물함, 프로필, Google·Apple 연동, 설정, 음향·진동·연출 감소, 언어 구조, 계정 삭제, 로딩·네트워크 오류·업데이트 안내를 구현한다. 광고 준비 중/광고 없음/시청 중/보상 확인 중/지급 완료 상태도 실제 동작에 연결한다. 버튼이 실제 화면과 API로 연결되어야 한다.

6. 매치3 엔진

6.1 기본 규칙
- 인접한 상하좌우 두 타일만 교환한다. 같은 색 3개 이상 가로/세로 매치를 제거한다. 2×2는 아래 특수 블록 생성 규칙에 따라 추가 인정한다.
- 유효 매치 또는 특수 블록 발동을 만드는 교환만 이동 1회를 소비한다. 무효 교환은 부드럽게 원위치로 돌아가며 이동을 소비하지 않는다.
- 보드 특수 블록 탭 발동은 이동 1회, 특수 블록끼리 교환은 조합 전체에 이동 1회만 소비한다.
- 줄바람·꽃폭탄·씨앗비행기와 일반 타일의 인접 교환은 3매치가 없어도 유효하며 특수 블록의 교환 도착 위치에서 발동한다. 무지개등은 교환 상대의 색을 제거한다. 교환과 발동 전체가 이동 1회다.
- 점수가 아니라 목표 완수가 승리 조건이다. 제한 시간은 기본 본편에 넣지 않는다.
- 중력 낙하 → 빈칸 보충 → 새 매치/연쇄 → 목표 갱신을 더 이상 변화가 없을 때까지 반복한다.
- 목표를 모두 완료하면 남은 이동이 0이어도 승리다. 마지막 교환 뒤 연쇄가 진행 중인데 실패창을 띄우지 않는다.
- 가능한 수가 없으면 이동·하트 차감 없이 재배열한다. 목표/장애물 상태를 보존하고 무한 재배열에 빠지지 않게 검증한다.

6.2 기본 타일
빨간 둥근 열매, 파란 물방울, 노란 해 메달, 초록 두 잎 새싹, 보라 다섯 꽃잎 꽃, 주황 도토리의 독자적인 6종을 만든다. 색과 실루엣으로 함께 구분한다. 초반에는 4종, 진행에 따라 5종과 6종을 사용한다. 모든 타일을 동일한 사각형에 색만 바꿔 만들지 않는다.

6.3 특수 블록
- 줄바람: 직선 4개. 가로 또는 세로 한 줄을 제거하는 바람 캡슐. 생성 방향은 horizontal run → row, vertical run → column으로 고정한다.
- 꽃폭탄: L/T 형태 5개 이상. 중심 포함 Chebyshev 거리 2 이내, 최대 5×5 범위에 타격한다. 지도 밖/없는 셀은 제외한다.
- 씨앗비행기: 같은 색 2×2. 출발 칸과 인접 상하좌우를 타격하고 목표 타일 하나로 날아가 타격한다. 목표 우선 로직은 우리 게임의 규칙으로 명시한다.
- 무지개등: 직선 5개 이상. 일반 타일과 교환하면 해당 색 전체 제거. 단독 탭하면 가장 많은 색의 일반 타일을 선택하며 동률은 고정 색 순서로 결정한다.

보드 위에서 생성하는 특수 블록과 인벤토리에서 소모하는 부스터를 별도 타입으로 정의한다. 자연 매치로 만든 특수 블록이 인벤토리를 소비하거나 증가시키지 않는다.

시작 전 부스터는 승인된 초기 보드의 일반 타일 칸에 결정론적으로 배치한다. 목표·장애물·튜토리얼 고정 칸을 덮어쓰지 않는다. 필요한 수만큼 배치 가능한지 먼저 검증하고, 부스터 배치까지 포함한 초기 상태를 run에 고정한 뒤 재고를 차감한다. 배치 불가인 선택을 소비하거나 효과 없이 시작하지 않는다.

6.4 조합
- 줄바람 + 줄바람: 중심 행·열 십자 타격.
- 줄바람 + 꽃폭탄: 중심을 기준으로 연속 3행과 3열 타격.
- 꽃폭탄 + 꽃폭탄: 중심에서 Chebyshev 거리 4 이내 넓은 범위 타격.
- 씨앗비행기 + 씨앗비행기: 비행체 3개가 서로 다른 유효 목표를 우선 선택한다. 유효 목표 부족 시 deterministic fallback을 사용한다.
- 씨앗비행기 + 줄바람/꽃폭탄: 선택한 목표로 해당 특수 블록을 운반해 발동한다.
- 무지개등 + 줄바람/꽃폭탄/씨앗비행기: 가장 많은 색의 일반 타일을 해당 특수 블록으로 변환한 뒤 고정 순서로 발동한다.
- 무지개등 + 무지개등: 모든 일반 타일 제거, 각 장애물의 제거 가능한 한 겹을 한 번 타격한다. 다층 장애물을 무조건 전부 지우지 않는다.

6.5 결정론과 충돌 규칙
- 같은 레벨 정의/버전, 엔진 버전, seed, 순서가 있는 행동 로그는 항상 같은 결과여야 한다.
- Math.random, 렌더 프레임 수, 실제 시간, 이펙트 파티클 수가 게임 난수에 영향을 주면 안 된다. 미술용 난수는 별도다.
- 동시 매치의 처리 순서, 특수 블록 우선순위, 생성 위치, 타격 중복, 낙하 순서, 동률 목표 선택을 명문화한다.
- 기본 생성 우선순위는 직선 5개 이상 > L/T > 2×2 > 직선 4개. 서로 독립적인 매치는 각각 처리한다.
- 생성 위치는 교환 도착 칸이 해당 매치에 포함되면 그 칸, 아니면 출발 칸, 둘 다 아니면 고정 행/열 순서를 사용한다.
- 하나의 effectId는 같은 장애물에 한 번만 피해를 준다. 서로 다른 효과의 추가 타격은 장애물 규칙에 따라 허용한다.
- 새로 생성한 특수 블록과 같은 처리 단계의 제거 대상이 충돌하는 경우를 명시하고 회귀 테스트를 만든다.
- 입력은 idle 상태에서만 승인한다. 애니메이션 완료와 논리 처리 완료를 구분하고 중복 탭으로 두 번 교환되지 않게 한다.
- 의도된 일괄 연쇄 상한을 넘으면 안전하게 정지·오류 기록하며 검증되지 않은 보상을 지급하지 않는다.
- 턴 순서는 행동 승인 → 매치/특수 효과/낙하/보충/연쇄 완료 → 목표 달성 시 승리 확정 → 미완료이면 턴 종료 장애물 갱신 1회 → 최종 목표/이동 수 판정이다. 턴 종료 장애물의 추가 결과가 다시 턴 종료 단계를 재실행하지 않는다. 이동을 소비하지 않는 인벤토리 부스터와 자동 재배열은 이끼 확산 등 턴 종료 효과를 발생시키지 않는다.

6.6 보드 데이터
셀 존재 여부, 바닥층, 일반 타일/특수 블록, 장애물층, 목표, 유입구, 낙하 연결을 분리한다. 없는 셀과 막힌 셀은 다르다. 분리된 구역도 명시된 유입구로 공급되게 한다. 포털과 이동 레인 등 추가 규칙은 구현·검증한 feature만 생성기가 사용한다. 구멍이 있는 보드를 단순히 모든 열에서 y+1로만 떨어뜨리지 않는다.

6.7 인벤토리 부스터의 정확한 효과
망치는 선택한 유효 셀에 타격 1회, 가로/세로 쓸기는 선택한 행/열의 유효 셀에 각각 타격 1회를 준다. 타격한 특수 블록은 그 위치에서 정상 연쇄 발동한다. 다층 장애물은 타격당 한 겹만 줄며 다중 셀 장애물은 인스턴스 기준으로 중복을 제거한다. 섞기는 이동 가능한 일반 타일과 보드 특수 블록을 보존한 채 재배열하고 고정 목표/장애물/바닥층은 유지한다. 초기 자동 매치와 수 없음 상태를 검사한다. 불가능한 대상 선택·취소·재배열 불가는 재고를 소모하지 않는다. 서버가 행동 순서와 유효 대상을 승인한 후에만 재고를 차감하며 동일 사용 명령은 한 번만 적용한다.

7. 장애물과 목표

다음 계열을 차례로 도입하되, 새 요소는 첫 등장 안내를 제공한다.
- 나무 상자: 인접 매치 또는 특수 효과로 1회 타격. 1~3겹 상태 이미지.
- 덩굴 잠금: 해당 칸 타일을 매치/타격해 잠금을 풀기 전 이동 제한. 타일 자체와 잠금 레이어 분리.
- 서리 바닥: 위 타일 제거로 한 겹 감소. 바닥층이므로 낙하하지 않는다.
- 떨어뜨릴 씨앗 주머니: 지정 출구로 운반하는 낙하 수집 목표. 제거 목표와 구별한다.
- 색상 화분: 지정 색 매치로 충전하고 완성 시 목표 수 감소.
- 확산 이끼: 한 수 동안 제거하지 못하면 플레이어 행동으로 인한 모든 연쇄가 끝난 턴 종료 단계에서 딱 1회, 허용된 인접 칸으로 정해진 규칙에 따라 확산한다. 낙하/연쇄 단계마다 반복 성장하지 않는다. 튜토리얼 후 사용한다.
- 정원 저장함: 고정된 타격/색 충전 조건을 충족하면 씨앗을 배출하는 다단계 목표.
- 후기 구조: 병목, 분리 구역, 포털, 이동 레인. 각각 검증 후 콘텐츠 버전으로 해금한다.

장애물마다 어떤 피해를 받는지, 낙하하는지, 중력을 막는지, 이동 가능한지, 목표에 어떻게 집계되는지, 어느 frame에 상태 이미지를 바꾸는지 정의한다. 목표 카운트가 실제 남은 대상과 일치해야 한다. 2칸 이상의 저장함은 obstacleInstanceId, anchor, footprint로 하나의 내구도와 목표를 공유하며 같은 effect가 두 칸에 닿아도 중복 피해/중복 집계하지 않는다.

8. 튜토리얼과 초반 플레이

첫 4판은 별도 고정 seed와 시작 보드로 설계한다. 안내는 한 번의 짧은 행동과 즉각적인 피드백으로 구성하고 장문의 도움말을 화면에 상시 배치하지 않는다.

- 1판: 상하좌우 교환 → 3개 매치 → 목표/이동 횟수 확인. 첫 교환만 손가락으로 안내하고 곧 자유 플레이로 전환한다.
- 2판: 직선 4개를 직접 맞춰 줄바람 생성 → 탭 또는 교환으로 사용.
- 3판: L/T 매치로 꽃폭탄 생성 → 상자 여러 개 제거.
- 4판: 2×2로 씨앗비행기 생성 → 떨어진 목표를 타격하는 체험.
- 5판: 무지개등 첫 등장 시 짧은 생성/사용 안내. 이후 특수 블록 조합과 인벤토리 부스터는 실제 첫 등장에만 짧게 안내한다.
- 첫 4판에 모든 조합·길드·상점·이벤트를 한꺼번에 가르치지 않는다. 4판 완료 후 무료 무제한 수령과 길드가 해금된다.

새 아이템이 등장했는데 설명 없이 진행되거나, 튜토리얼이 없는 목표를 처음부터 요구하지 않는다. 안내 영역은 실제 셀/버튼 좌표를 따라간다. 손가락·강조 프레임·말풍선·dim overlay도 이미지다. 튜토리얼 상태와 완료 flag를 저장하고 앱 재시작 시 해당 단계부터 복구한다. 건너뛰기와 다시 보기를 지원한다. 설명을 따르기 위한 소모품은 별도 무료 제공하며 구매를 강요하지 않는다. 첫 4판은 유료 구매 제안을 띄우지 않는다. 하트 규칙 자체는 튜토리얼에도 동일하게 적용한다.

자유 플레이 중 예정한 판보다 먼저 새 특수 블록이 만들어지면 그 시점에 해당 첫 등장 안내를 한 번 보여주고 학습 상태를 기록한다. 예정된 판에서 같은 설명을 길게 반복하지 않으며, 튜토리얼 순서를 맞추려고 합법적인 특수 블록 생성을 몰래 취소하지 않는다.

9. 레벨이 끝나지 않는 콘텐츠와 난이도

9.1 공급 구조
- 1~30레벨: 도입 순서와 재미를 직접 검토한 고정 정의/seed.
- 31~200레벨: 여러 보드 형태, 장애물, 목표, 색 수를 조합하되 검증을 통과한 데이터 팩을 제공한다.
- 201 이후: 버전이 고정된 템플릿과 seed를 조합하여 다음 번호를 계속 제공한다. 200에서 완료 화면을 띄우거나 더미 레벨로 막지 않는다.
- 후보 생성 → 정적 검사 → 무구매 자동 플레이/승리 경로 검증 → 승인된 팩 게시를 분리한다.
- 무거운 탐색을 플레이어의 시작 요청 안에서 수행하지 않는다. 빌드 도구 또는 적절한 비동기 작업이 사전에 승인 풀을 보충하고 R2에 팩을 저장한다.
- 예비 풀이 부족하면 이미 승인된 구조의 안전한 변형 풀을 사용하며, 검증하지 않은 임의 seed를 즉석 공개하지 않는다.
- 출시 범위에서 1,000과 10,000레벨 등 먼 번호도 생성·검증·플레이할 수 있음을 확인한다. 생성기 feature flag보다 구현이 앞서 있어야 한다.

9.2 난이도 곡선
장기적으로 더 어려워지고 복잡해지되 모든 판이 직전보다 더 어려울 필요는 없다. 일반 → 도전 → 일반 → 어려움 → 짧은 회복 구간의 리듬을 만든다. 20~50레벨 단위 구간의 평균 복잡도를 높인다.

조절 축은 색 종류, 보드 형태, 통로 폭, 장애물 밀도/겹수, 목표 개수, 접근 순서, 낙하 경로, 특수 블록 조합 필요성이다. 이동 횟수는 마지막 보정 수단으로 사용한다. 보드를 무한히 키우거나 이동 수를 계속 줄여 해결 불가능하게 만들지 않는다. 모바일 보드와 인지 부담에는 상한을 두고, 상위 구간에서는 새로운 조합과 숙련도를 요구한다. 끝이 없는 레벨 공급과 끝없이 새로운 미술의 자동 생산을 혼동하지 않는다.

9.3 공개 전 검증
- 허용하지 않은 초기 자동 매치가 없는가.
- 최소 하나의 합법적 수가 있고 무료 재배열이 종료되는가.
- 목표 수량이 배치와 생성 규칙으로 달성 가능한가.
- 목표 구역/출구가 접근 가능하고 중력 그래프가 모순되지 않는가.
- 구매 부스터를 쓰지 않는 승리 행동 로그가 적어도 하나 존재하고 같은 엔진으로 재생되는가.
- 자동 탐색이 못 푼 판을 즉시 불가능 판이라고 단정하지 말고, 미검증 후보로 격리한다. 승인 기준을 낮춰 유저에게 배포하지 않는다.
- 여러 정책의 봇으로 수백~수천 시드를 평가하고 보고서에 정책·표본·버전을 기록한다. 봇 성공률을 사람의 실제 성공률이라고 표시하지 않는다.
- 결제 여부나 패배 직후 상황에 따라 진행 중인 seed, 타일 드롭, 목표를 몰래 바꾸지 않는다.
- 플레이 테스트와 실제 텔레메트리로 수치를 조정하되 새 콘텐츠 버전의 다음 판부터 적용한다.

10. 하트와 무료 무제한 시간

아래 수치는 이번 게임의 초기 운영값이다. 서버 config로 바꾸되 진행 중 판의 조건은 보존한다.

- 기본 최대 하트: 5.
- 자연 회복: 3,600초마다 1개. 앱을 꺼도 회복한다.
- 신규 판 시작을 서버가 승인하면 하트 1개 소비. 승리/패배와 무관하다.
- 재도전은 새 판이므로 다시 소비. 동일 runId의 재접속/복구/추가 이동 구매는 추가 소비하지 않는다.
- 하트 0이고 무제한이 아니면 새 판 시작을 거절한다.
- 부족 상태에서 추가로 하트를 사용해도 기존 회복 타이머를 리셋하지 않는다. 59분이 지났는데 추가 소모했다고 다시 60분이 되어서는 안 된다.
- 최대치에 도달하면 초과 회복 시간을 적립하지 않는다. 최대치에서 처음 소모할 때 새 회복 주기를 시작한다.
- 무제한 상태에서도 자연 회복은 계속된다.

10.1 무료 무제한은 수령형으로 고정한다
이번 기본값은 모든 유저에게 동시에 열리는 00/04/08시 고정 시간창이 아니다. 플레이어가 4시간마다 한 번 받을 수 있는 무료 30분 보너스다.

- 4판을 완료하면 첫 무료 수령이 가능하다.
- 받기 버튼을 누르고 서버가 승인한 순간부터 30분을 부여한다.
- 다음 수령 가능 시각 = 직전 수령 승인 시각 + 14,400초. 무제한 종료 후 4시간이 아니다.
- 예: 10:00 수령 시 10:30까지 이용하고 14:00부터 다시 수령 가능. 16:00에 실제 수령하면 다음은 20:00.
- 미접속 중 이용권이 여러 장 누적되지 않는다. 받을 수 있는 권리는 최대 1회분이다.
- 수령 후 앱을 종료해도 시간이 흐른다. 단말 시계/시간대/재설치로 시간을 늘릴 수 없다.
- 이미 다른 무제한 시간이 있다면 unlimitedUntil = max(serverNow, unlimitedUntil) + 1,800초로 이어 붙인다. 무료·유료 시간이 겹쳐 사라지지 않게 한다. 구매형 무제한도 동일한 시간 원장을 사용한다.
- 무제한이 유효한 시점에 승인된 판은 하트 0개로 시작한다. 판 도중 무제한이 끝나도 소급 차감하지 않는다.
- 시작 당시 하트를 소비한 판에 나중에 무제한이 켜져도 소비를 자동 환불하지 않는다.
- 서버 UTC timestamp가 권위다. UI는 서버 시각과 monotonic elapsed로 카운트다운을 표시하고 앱 복귀 시 재동기화한다.
- 수령 버튼 중복 탭, 기기 2대 동시 요청, 응답 유실에 동일 수령이 두 번 지급되지 않아야 한다.

10.2 시작 처리
플레이 전 필수 에셋을 준비한다. 그 뒤 idempotencyKey를 가진 시작 API가 하트 검사/차감, 선택 부스터 차감, run 생성을 하나의 거래로 처리한다. 응답만 유실되면 같은 키로 재요청하거나 활성 run을 복구한다. 클라이언트가 임의로 하트를 환불하지 않는다. 한 계정에는 동시에 하나의 활성 run만 허용한다. 예기치 않은 앱 종료는 즉시 패배로 처리하지 않고 같은 판으로 복귀하게 한다.

11. 길드와 지원

11.1 기본 기능
- 4판 완료, 즉 5레벨 진입 시 길드 해금.
- 최대 30명. 공개 가입/승인 가입, 검색, 길드명·소개·미리 제작한 문장/색상·최소 레벨, 역할, 탈퇴/추방을 구현한다.
- 지원 피드, 멤버 목록, 짧은 텍스트 채팅, 공지, 신고/차단/도배 제한을 제공한다.
- 초기 소규모 서비스에서도 길드 지원 기능이 실제로 동작해야 한다. 가짜 길드원이 기부한 것처럼 자동 연출하지 않는다.

11.2 하트 지원
- 요청 간격 4시간, 요청 하나의 유효기간 4시간, 요청당 최대 5개.
- 같은 요청에 같은 멤버는 1회만, 자기 자신에게는 지원 불가.
- 지원자는 자신의 플레이용 하트를 잃지 않는다. 별도 지원 횟수를 사용하며 초기 일일 한도는 10회다.
- 수신자의 일일 하트 수신 한도는 10개, 미수령 보관 상한은 20개로 시작한다. 이를 원작의 수치라고 표시하지 않는다.
- 선물은 우편함에 보관하고 하트 최대치일 때 자동 사용/삭제하지 않는다. 초기 정책은 하트 선물에 유효기간을 두지 않는 대신 저장 상한을 둔다.
- 선물 수령 시 현재 여유만큼만 반영하고 나머지는 보관한다. 우편함 한도가 찼으면 새 요청/전송 전에 알린다.
- 길드·광고 등 일일 제한은 초기 운영값으로 UTC 00:00에 갱신하고 화면에는 다음 갱신 시각을 현지 시간으로 표시한다. 길드 이동과 기기 시간대 변경으로 초기화하지 않는다.

11.3 아이템 지원
- 기본 지원 허용 목록: 인벤토리 망치, 가로 쓸기, 세로 쓸기, 섞기. 지원 이벤트 설정으로 목록을 관리한다.
- 요청당 1개, 요청 간격 4시간, 보내기/받기 각각 일일 3개로 시작한다.
- 하트와 달리 아이템은 보내는 사람의 실제 재고에서 1개 차감한다.
- 지원 가능한 비귀속 재고에서만 차감한다. 광고로 받은 보상과 광고 보상 코인으로 구매한 아이템은 계정 귀속으로 관리하여 지원할 수 없게 한다. UI에는 전체 수량과 별도로 '지원 가능 수량'을 표시한다.
- 보내기 승인 시 송신 재고 차감과 수신 선물 생성이 같은 D1 거래여야 한다. 수령 시 선물 상태 변경과 수신 재고 증가도 같은 거래여야 한다.
- 코인, 별, 구매 영수증, 시즌 패스 권한, 무료 무제한 수령권은 지원할 수 없다.
- 보내는 순간 양쪽 길드 소속, 요청 유효성, 한도, 재고를 다시 검사한다. 탈퇴로 미완료 요청은 닫되 이미 확정된 선물은 유지한다.
- 지원 보상은 기본적으로 도움 횟수/비금전적 기여 점수다. 다계정 지원만으로 코인이 무한 생성되지 않게 한다.

12. 재화와 비즈니스 모델

12.1 출시 기본 방침
인앱 구매와 유저가 직접 선택하는 보상형 광고를 함께 사용한다. 기본 광고 공급자는 AdMob Rewarded로 두고 교체 가능한 adapter로 분리한다. 자동 전면 광고, 배너, 앱 실행 광고, 판 종료 자동 광고, 강제 보상형 광고는 넣지 않는다. 코인은 소모품 구매/이어하기/하트 보충에, 별은 정원 복원에 사용한다. 두 재화를 합치지 않는다. 무료 플레이에도 정원과 다음 레벨로 가는 정상적인 경로를 제공한다.

12.2 초기 경제 수치
이 수치는 매출 최적값이 아니라 플레이 테스트용 시작점이다. 서버 economy config에서 관리한다.
- 신규 코인 500, 하트 5.
- 최초 클리어 코인: 일반 50 / 어려움 75 / 매우 어려움 100.
- 최초 클리어 별 1. 동일 레벨의 최초 보상을 재수령할 수 없다.
- 추가 이동 +5: 같은 판에서 첫 300 / 두 번째 600 / 세 번째 900코인, 최대 3회. 비용을 누르기 전에 보여준다.
- 하트 1개 100코인, 전체 충전은 부족한 개수 ×100코인. 이미 가진 하트까지 다시 구매시키지 않는다.
- 인벤토리 망치 150, 가로/세로 쓸기 각 250, 섞기 150코인.
- 시작 전 줄바람 150, 꽃폭탄 200, 무지개등 300코인. 시작 전 각 종류 1개씩 선택 가능.
- 게임 중 인벤토리 부스터는 이동 횟수를 소비하지 않는다. 무료 지급과 실제 재고 차감 내역을 명확히 관리한다.
- 구매 부스터를 요구하는 목표나 결제를 해야만 통과 가능한 레벨은 만들지 않는다.

12.3 실제 구현할 상품
- 코인 패키지 6종: 1,000 / 2,500 / 6,000 / 15,000 / 40,000 / 100,000코인의 테스트 카탈로그.
- 계정당 1회 스타터 팩: 코인과 소모품의 확정 수량을 명시. 강제 카운트다운을 붙이지 않는다.
- 부스터 패키지: 코인·소모품·무제한 시간의 구성과 수량을 구매 전에 표시.
- 정원 패스: 28일 시즌, 30단계, 무료/유료 보상선, 클리어로 포인트 획득, 코인·부스터·프로필 장식·길드 선물. 자동 갱신 구독이 아닌 해당 시즌 1회 구매로 시작한다.
- 패스가 코어 게임 규칙이나 숨겨진 RNG를 유리하게 바꾸지 않는다. 기본 하트 최대 5는 유지하며 최대치 확장은 초기 범위에서 제외한다.
- 가격은 App Store/Google Play가 반환하는 현지화 가격을 사용한다. 실결제 가격을 임의 문자열로 하드코딩하지 않는다.
- 유료 저금통·확률형 뽑기는 이번 기본 범위에서 제외한다.

12.4 운영 이벤트
일일 보상, 개인 목표 누적 이벤트, 길드 공동 진행 보상, 시즌 패스를 데이터로 구성한다. 실제 시작/종료 시각과 보상 수령 상태를 서버에서 관리한다. 최초 유저에게 이벤트 팝업을 연속 노출하지 않는다. 구매 제안은 초반 튜토리얼 뒤 자연스러운 화면 전환에서 제한적으로 노출한다.

12.5 선택형 보상 광고

유저가 '광고 보고 하트 +1' 또는 '광고 보고 코인 2배'를 직접 눌렀을 때만 광고를 보여준다. 시청 전에 무엇을 얼마나 받는지 정확하게 표시한다. 광고를 보지 않거나 중간에 닫아도 이미 받은 보상·하트·진행을 빼앗지 않는다. 광고 클릭이나 광고 상품 설치를 보상 조건으로 만들지 않는다.

배치 A: 하트 충전
- 광고 완료 1회당 개인용 하트 1개. 초기 한도는 하루 5회이며 원격 설정으로 조정 가능하다.
- 하트가 기본 상한보다 적고 무제한 상태가 아닐 때 제안한다. 볼 필요가 없는 상태에서 시청을 유도하지 않는다.
- 시청 중 자연 회복/다른 기기 활동으로 하트가 가득 차도 약속한 1개를 잃지 않는다. 이미 승인된 광고 intent에 예약된 개인용 미수령 하트로 보관하고 여유가 생기면 사용한다.
- 개인용 광고 하트는 길드로 양도할 수 없다. 길드의 별도 무료 지원 횟수와 혼동하지 않는다.

배치 B: 클리어 코인 2배
- 기본 클리어 코인과 별은 서버 승리 검증 후 광고와 관계없이 먼저 지급한다.
- 광고 완료 시 해당 판에서 확정한 기본 클리어 코인과 동일한 양을 한 번 추가 지급한다. 기본 50이면 추가 50, 총 100이다.
- 별, 이벤트 포인트, 패스 포인트, 지역 보상, 아이템, 구매 보상은 두 배로 만들지 않는다. 버튼 문구는 모호한 '보상 2배' 대신 '코인 2배'다.
- 같은 runId의 보너스는 1회, 초기 일일 한도는 10회다. 실패 판과 최초 보상이 없는 연습/재플레이는 대상이 아니다.
- 광고를 선택하지 않고 바로 다음 레벨/홈으로 이동할 수 있다. 광고 준비 실패 시 다시 누르거나 기본 보상만 받고 이동할 수 있다.

4시간마다 받는 무료 30분 무제한은 광고 없이 유지한다. 시작 전/플레이 도중 광고를 자동으로 켜지 않는다. 추가 광고 배치는 별도 config로 확장 가능하게 하되 첫 구현의 활성 배치는 위 두 가지다. 첫 4판 동안 광고 제안은 숨긴다.

광고 보상은 계정 귀속으로 관리한다. 광고 코인과 일반 코인은 서버 원장에서 구분하고, 화면에서는 총액을 표시하되 아이템 지원 가능 여부를 정확히 표시한다. 광고 코인으로 구매한 아이템은 기부 불가다. 혼합 결제는 아이템 한 개 단위로 출처를 기록하며 광고 코인이 일부라도 쓰인 그 아이템은 귀속으로 처리한다. 기본 소비 우선순위는 자기 사용처에서 귀속 코인/아이템 먼저이며, 지원 기능은 비귀속 재고만 사용한다. 광고 보상을 타인에게 이전 가능한 재화로 세탁하는 경로를 만들지 않는다.

12.6 광고 보상 서버 검증

- Capacitor에서 Google Mobile Ads 네이티브 SDK를 지원하는 브리지를 사용한다. 선택 브리지가 Rewarded, SSV custom_data, 보상/닫기/오류 콜백, 동의 흐름을 실제 지원하는지 확인한다. 부족한 기능은 작은 네이티브 브리지로 구현하며 웹 iframe으로 흉내 내지 않는다.
- 유저가 시청을 선택하면 POST /ads/reward-intents로 userId, placement, runId/기본 보상 원장, 확정 보상량, nonce, 유효시간, 광고 단위, 쿼터 예약이 연결된 1회성 intent를 만든다. 시청 조건과 한도는 서버에서 승인한다. 브리지가 이미 로드한 광고의 SSV 값을 변경할 수 있는지 확인하며, 불가능하면 intent 발급 → 해당 값을 넣어 광고 로드 → 시청 순서로 처리하고 로드 실패 시 예약을 해제한다.
- 광고 SDK의 custom_data에는 서버가 발급한 opaque intentId를 연결한다. 보상량과 사용자를 클라이언트 임의 문자열만으로 결정하지 않는다.
- Workers의 공개 SSV 콜백 엔드포인트는 AdMob 공개키, key_id, 원본 서명 대상 query와 ECDSA 서명을 공식 명세대로 검증한다. 서명 검증 전에 URL을 decode/reorder/reserialize하여 서명 원문을 바꾸지 않는다. 검증 후 custom_data를 해석한다.
- 키 캐시/갱신, signature 인코딩, 허용 ad_unit, 사용자 귀속, intent, signed timestamp, 허용 보상 종류를 검사한다. 검증된 라이브러리/테스트 벡터를 사용하고 암호 알고리즘을 임의 작성하지 않는다.
- 클라이언트의 보상 콜백은 '보상 확인 중' UI와 상태 조회에 사용한다. 닫기 콜백은 보상 증명이 아니다. 실제 재화는 검증된 SSV를 근거로 D1에서 확정한다.
- provider + transaction_id, intentId, userId + runId + coin_bonus 고유 제약으로 한 번만 지급한다. 콜백이 클라이언트보다 먼저 와도, 여러 번 와도, 앱 종료 뒤 와도 동일하게 처리한다.
- 광고 로딩 실패/시청 취소는 확정 수령 횟수를 소모하지 않는다. quota 예약과 실제 지급 횟수를 구분하고 중복 시청 intent를 제한한다.
- 유효한 시청에 대한 SSV가 늦게 도착했다는 이유만으로 보상을 소멸시키지 않는다. 시청 승인 시각·서명된 보상 시각·콜백 도착 시각을 구분하며, 만료 처리와 늦은 콜백의 경합을 검증한다. 처리 내역 조회와 지연 지급 복구를 제공한다.
- 광고 공급자가 무한 재전송한다고 가정하지 않는다. 검증한 콜백을 내구성 있는 inbox/거래에 저장한 뒤 성공 응답하고 내부 지급은 재시도 가능하게 한다. 공급자 콜백 자체를 끝내 받지 못한 경우 확인 중 기록과 운영자 검토 경로를 남기며, 단순 클라이언트 주장만으로 운영 재화를 무제한 생성하지 않는다.
- 지급 대상은 광고를 볼 당시 intent에 연결한 계정이다. 시청 후 계정 전환이나 다음 레벨 진입, 날짜/설정 변경이 있어도 확정한 보상량과 수신자를 바꾸지 않는다. 광고 길이를 임의로 30초라고 약속하거나 단순 타이머로 완료 여부를 판단하지 않는다.
- 짧은 확인 대기 뒤에도 SSV가 없으면 계속 볼 수 있는 '확인 중' 내역으로 남기고 홈으로 돌아갈 수 있게 한다. 다시 광고를 봐야 기존 보상을 주는 구조로 만들지 않는다.
- 광고 없음/no-fill, SDK 로드 실패, 시청 실패, 미완료 종료, 보상 확인 중, 지급 완료를 구분한다. 광고 없는 지역이나 기기에서도 기본 플레이·기본 보상·자연 회복은 동작한다.
- UMP 등 공식 동의 흐름과 privacy options를 해당 플랫폼/지역 설정에 맞게 연결한다. 광고 요청 가능 상태를 확인한 뒤 요청하고, 추적 동의 거절 자체를 게임이나 기본 보상을 막는 조건으로 사용하지 않는다.
- 개발/테스트는 테스트 광고 단위와 개발 전용 가짜 콜백을 분리한다. 운영 환경에 임의 보상 지급용 debug endpoint를 포함하지 않는다.

13. 정원 복원과 장기 진행

퍼즐 최초 클리어 별로 홈 장면의 복원 작업을 수행한다. 초기에 하늘 정원, 온실 작업실, 분수 테라스 3개 지역을 실제 이미지로 완성하고 지역마다 6개 복원 작업을 제공한다. 초기 작업 비용은 별 1~3개 범위에서 단계별로 설정한다.

지역 배경에 UI와 모든 오브젝트를 합치지 않는다. 배경·수리 전 물체·수리 후 물체·장식·그림자·복원 효과를 레이어로 만든다. 복원 버튼을 누르면 별 차감과 작업 완료/지역 보상 지급이 서버 거래로 처리되고 장면의 해당 오브젝트가 변한다. 비용과 결과를 미리 알 수 있어야 한다.

이후 지역은 콘텐츠 팩으로 추가할 수 있게 한다. 준비된 지역을 모두 복원해도 퍼즐은 계속 진행한다. 지역 콘텐츠가 유한하다는 이유로 레벨을 막거나 별을 잃게 하지 않는다. 신규 지역을 기다리는 동안 별과 이벤트 진행을 보존하고 완성된 정원을 볼 수 있게 한다.

14. 계정과 저장

- 첫 실행에서 서버 guest userId와 세션을 발급하고 임의 닉네임을 만든다. 기기 ID만으로 인증하지 않는다.
- refresh token은 네이티브 보안 저장소에 보관하고 클라이언트 번들에 서버 비밀키를 넣지 않는다.
- Google과 Apple 계정 연동을 모두 지원한다. 각 플랫폼에서 공식적으로 지원되는 네이티브/웹 인증 흐름을 사용한다.
- 서버가 서명, issuer, audience, expiry, 해당 흐름의 nonce/state/PKCE 등을 검증한다. 클라이언트가 보낸 이메일만 믿고 계정을 연결하지 않는다.
- provider + sub를 계정 식별 연결 키로 사용한다. 하나의 userId에 두 공급자를 모두 연결할 수 있다.
- 연결할 공급자 계정에 기존 저장이 없으면 현재 guest userId에 연결해 진행·구매·재화를 유지한다.
- 이미 다른 userId의 저장이 있으면 두 진행 정보를 보여주고 기존 계정으로 전환 또는 취소를 선택하게 한다. 코인·아이템을 자동 합산하거나 기존 저장을 덮어쓰지 않는다.
- 연결과 계정 전환은 활성 run 정산/보류 상태를 확인하고 진행한다. 전환 취소로 진행을 잃지 않게 한다.
- 게스트 구매도 안정적인 서버 userId에 귀속하고, 기기 변경을 위한 계정 연동을 비강제적으로 안내한다.
- 계정 삭제, 세션 해제, 구매 권한 동기화, 재설치/다른 기기 로그인 복구 흐름을 구현한다.
- 개인정보·토큰·영수증 원문을 일반 로그나 공개 R2에 넣지 않는다.

15. 서버 권위와 거래 안전성

15.1 권위 데이터
하트, 코인, 별, 인벤토리, 무제한 시간, 진행 레벨, 이벤트 보상, 패스 권한, 길드 지원, 결제는 서버가 결정한다. 클라이언트 localStorage는 최종 권위가 아니다.

시작 API는 runId, levelId, levelVersion, engineVersion, contentVersion, 승인된 seed, 초기 이동 횟수, 승인된 부스터, 시작 시 하트 소비/무제한 조건을 확정한다. seed는 승인 팩의 levelDefinition + approvedSeed + engineVersion 조합에서만 선택한다. 재도전도 검증된 변형 풀을 사용하며 시작할 때마다 미검증 난수를 새로 주입하지 않는다. 클라이언트는 순서가 있는 행동 로그를 제출한다. 서버는 같은 엔진으로 합법적 이동과 최종 상태를 재생해 승패를 검증한 뒤 보상과 다음 레벨을 확정한다. 클라이언트가 보낸 win=true나 코인 수를 그대로 저장하지 않는다.

행동 로그는 중복 sequence와 비정상 길이, 오래된 버전, 허용하지 않은 부스터, 불가능한 좌표를 거절한다. 해시는 무결성 비교 수단이며 서버 재생 검증을 대신하는 보안 장치라고 주장하지 않는다. 재생 검증만으로 모든 자동 플레이를 막았다고 주장하지 않는다.

15.2 D1 거래
모든 지갑·인벤토리·선물 원장을 같은 D1 데이터베이스에 두어 초기 교차 사용자 거래를 단순화한다. 각 재화 변경의 이유, sourceId, delta, 서버 시각을 원장에 기록한다. balance >= 0과 고유 제약을 DB에 둔다.

D1 batch에 SQL을 모았다는 이유만으로 비즈니스 조건 검증이 원자적이라고 가정하지 않는다. 조건부 UPDATE가 0행을 바꾸는 것은 SQL 오류가 아니다. 하트 부족·재고 부족·요청 만료·한도 초과이면 전체 작업이 실패하도록 DB 제약, 검증된 트리거 또는 동등하게 안전한 조건부 거래 구조를 구현한다. 거래 밖에서 잔액을 읽고 나중에 차감하는 read-modify-write로 끝내지 않는다.

Durable Object와 D1, 또는 서로 다른 Durable Object를 하나의 원자적 DB 거래처럼 취급하지 않는다. D1 성공 후 알림이 실패하면 같은 이벤트를 다시 알리고 재화를 다시 지급하지 않는다. outbox나 동등한 복구 경로를 둔다. Queues와 웹훅은 중복 도착을 전제로 처리한다.

필수 고유 키의 예:
- 시작: userId + idempotencyKey
- 판 보상: runId + rewardType
- 최초 레벨 보상: userId + levelId + rewardType
- 하트 지원: requestId + senderId
- 선물 수령: giftId
- 무료 무제한 수령: userId + claim sequence 및 쿨다운 조건
- Google 결제: purchaseToken
- Apple 결제: environment + transactionId
- 시즌 소유: userId + seasonId
- 광고 보상: provider + transactionId, intentId, userId + runId + coin_bonus
- 외부 이벤트: provider + eventId

15.3 통신과 재접속
새 판 시작·구매·재화 사용·지원·결과 확정은 온라인 서버 승인이 필요하다. 이미 시작한 퍼즐은 잠깐 통신이 끊겨도 일반 이동을 진행하며 행동 로그와 snapshot을 로컬에 보관할 수 있다. 이 동안 새 인벤토리 부스터 사용과 결제는 재연결을 기다린다. 이미 승인된 사용 명령의 재생은 가능하다. 결과는 검증 대기 상태로 보관하고 서버 확정 전에 다음 레벨이나 보상을 제공하지 않는다.

네트워크 오류와 정상 패배를 구분한다. 같은 판을 이어받고 추가 하트를 차감하지 않는다. 장시간 미완료 run의 만료 정책을 문서화하되 시작 직후 앱 전환을 실패로 취급하지 않는다. 기본 복구 보존은 24시간이며 정상 종료된 판은 다시 보상받을 수 없다. 외부 오류 보상은 서버가 확인 가능한 원장에 근거해 지급한다.

15.4 스키마와 API 계약
플레이어/인증 연결/세션, 일반·귀속 코인 지갑, 하트 상태, 일반·귀속 인벤토리, run과 행동, 레벨/콘텐츠 버전, 보상·소비 원장, 무제한 수령, 길드/멤버/채팅/요청/선물, 시즌/상품/구매, reward_intents, ad_callbacks, ad_daily_usage, outbox의 관계와 제약을 실제 D1 migrations로 작성한다.

게스트 생성, 계정 연동/전환, 내 상태 조회, 판 시작/재개/부스터 사용/추가 이동/정산, 하트 선물 수령, 무료 무제한 수령, 길드 지원, 상품/구매 검증, 광고 intent/지급 상태/SSV에 대해 공유 TypeScript 계약과 입력 검증을 구현한다. 시간·코인·인벤토리의 변경 응답에는 서버 시각과 최신 상태 버전을 함께 반환한다. 광고/구매 콜백은 각각 공급자 검증을 사용하고 일반 사용자 API는 사용자 세션을 사용한다.

16. 실제 인앱 결제

- App Store/Google Play 네이티브 결제를 사용한다. 웹 결제창으로 게임 내 구매를 임의 대체하지 않는다.
- 상품 조회, 구매 진행, 취소, 보류, 검증 중, 완료, 오류 상태를 구분한다.
- 서버에서 상품 ID, 앱 식별자, 구매 상태, environment, 사용자 귀속, 서명/영수증을 검증한다.
- Google PENDING에는 지급하지 않고 PURCHASED 확인 후 지급한다. purchaseToken을 중복 키로 쓰며 orderId만으로 식별하지 않는다.
- Apple은 서명된 거래와 App Store Server API/Notifications에 맞춰 검증한다.
- 서버 지급 원장 확정 후 acknowledge/consume/finish를 각 플랫폼에 맞게 멱등적으로 처리한다.
- 응답 유실, 지연 승인, 중복 웹훅, 취소/환불, 앱 재설치에 중복 지급되지 않아야 한다.
- 소모품 구매 복원을 이유로 이미 쓴 코인을 다시 주지 않는다. 서버의 현재 잔액과 유효한 비소모성/시즌 권한을 동기화한다.
- 실제 키와 상품 등록이 없으면 개발용 결제 adapter를 분리하고 운영 빌드에 들어가지 않게 한다. 실제 결제 검증까지 성공했다고 허위 보고하지 않는다.
- 비밀키는 Workers secrets와 플랫폼 설정으로 관리하고 .env.example에는 이름과 예시만 둔다.

17. 이미지 제작과 파일 파이프라인

17.1 제작 순서
스타일 시트와 마스코트 기준 → 기본 타일 6종 → 버튼/패널/프레임 기준 → 홈/게임 배경 → 특수 블록/장애물 → 기능 UI → VFX/캐릭터 프레임 → 실제 화면 조립 → 검수 순서로 진행한다. 아래 부록의 영문 프롬프트를 공통 Style Lock과 결합한다.

사용 가능한 이미지 생성 도구를 확인하고 실제 에셋을 생성해 프로젝트에 연결한다. 프롬프트 목록만 작성해 놓고 이미지 제작을 완료했다고 하지 않는다. 생성 도구가 없거나 제한에 걸린 경우에는 에셋 manifest와 개별 프롬프트, 정확히 부족한 파일을 남기고 엔진/서버/흐름 작업은 계속 진행한다. 임시 도형을 최종 미술로 포장하지 않는다. 최초의 자체 스타일 기준을 이후 생성의 참조로 계속 사용한다.

17.2 출력 규격
- 배경 런타임 목표: 1080×2340, 다양한 화면비에서 crop할 수 있는 여백과 safe area 포함. 생성 모델이 이 크기를 직접 지원하지 않으면 가까운 비율로 생성한 뒤 적절히 확장/크롭/리사이즈한다. 가로세로를 따로 늘이지 않는다.
- 타일·아이콘 원본: 256×256 또는 그보다 큰 동일 정사각 캔버스. 실제 배치용 축소본을 만든다. 물체는 캔버스의 약 76~82%를 차지한다.
- 버튼: 예시 원본 768×256. normal/pressed/disabled 모두 같은 캔버스·pivot·slice 경계를 유지한다.
- 패널·프레임: 비율별 원본과 명시적인 9-slice metadata. 장식 코너는 늘어나지 않는다.
- 캐릭터 원본은 동일 캔버스, VFX는 효과 크기에 따라 128~512px 런타임 프레임.
- 알파가 필요한 자산은 실제 투명 PNG. 런타임 WebP 등의 사용은 목표 플랫폼 디코딩·알파 품질을 확인한 뒤 결정한다.
- atlas 기본 2048×2048 이하, 화면/용도별 분리, 2~4px padding과 edge extrusion. 원본 프레임과 JSON metadata를 함께 보관한다.
- 프롬프트에 크기를 썼다는 이유로 규격이 맞았다고 간주하지 않는다. 실제 파일의 width/height/alpha/trim을 검사하고 최종 규격을 맞춘다.

17.3 애니메이션
이미지 시퀀스/atlas와 스프라이트 transform을 사용한다. 프레임 애니메이션은 보통 12~24fps, 화면 렌더링은 60fps를 목표로 한다.

- swap: 기본 타일 이미지의 100~150ms 이동 보간.
- 타일 pop: 8프레임, 24fps, 색상별 파편과 작은 별 조각.
- 줄바람: 발사 8프레임 + 이동하는 head 이미지 + 반복 가능한 trail 이미지 + 6프레임 impact.
- 꽃폭탄: 12프레임, 24fps. 작은 준비 → 원형 꽃가루 폭발 → 파편 → 소멸.
- 씨앗비행기: 출발 6프레임 + 비행 loop 8프레임 + 도착 8프레임. 비행 경로는 코드로 계산하되 모든 시각 재료는 이미지.
- 무지개등: 충전 12프레임 + 이미지 광선/작은 입자 + 목표 pop. 긴 광선은 head/body/tail 이미지로 조합한다.
- 장애물: 피격 4~6프레임, 파괴 8~12프레임. 내구도별 상태 이미지 유지.
- 승리: 주요 연출 1~2초, 이미지 confetti와 보상 이동. 다음 행동을 장시간 막지 않는다.
- 마스코트: idle/기쁨/응원/실패 반응. 원본 외형과 pivot을 고정하고 과도하게 계속 움직이지 않는다.
- 튜토리얼: 손가락 이미지의 탭/스와이프, 강조 프레임, 이미지 말풍선.

같은 물체를 매 프레임 독립적인 디자인으로 다시 생성하지 않는다. 기준 이미지 편집과 고정 keyframe 계획을 사용한다. AI가 만든 격자형 sprite sheet의 셀/개수/정렬을 믿고 임의 잘라 쓰지 않는다. 검수한 개별 프레임을 deterministic packing 도구로 묶는다. 자동 trim을 사용할 경우 originalSize, offset, pivot을 복원해 흔들림을 막는다.

17.4 런타임 성능
이미지의 압축 용량과 디코딩/GPU 메모리를 구분한다. RGBA8 2048×2048 기본 픽셀은 16MiB이고 4096×4096은 64MiB이며 추가 메모리는 별도다. 모든 장면의 atlas를 동시에 올리지 않는다. 필요한 장면만 선로딩하고 사용하지 않는 texture를 해제한다. 타일·파편은 pooling하고 과도한 투명 픽셀·overdraw를 줄인다. 낮은 사양에서는 이미지 입자 수와 장식 애니메이션을 줄이되 퍼즐 결과는 동일하게 유지한다.

17.5 manifest
모든 에셋을 asset-manifest.json에서 관리한다. id, category, sourcePromptId, sourcePath, runtimePath, width, height, logicalSize, alpha, pivot, sliceInsets, originalSize/trimOffset, frames/fps/loop, atlasGroup, contentHash, safeArea, generationReference를 필요에 맞게 기록한다. UI 코드에 임의 파일명을 흩뿌리지 않는다. URL 실패와 버전 불일치를 검출한다.

17.6 소리와 진동
버튼, 교환, 무효 교환, 매치, 특수 블록 생성/발동/조합, 장애물 파괴, 보상, 승리/실패에 어울리는 짧은 효과음과 조용한 홈/퍼즐 BGM을 연결한다. 사용 가능한 생성 도구 또는 사용 권리가 확인된 음원을 사용하고 원작 소리를 추출하지 않는다. 소리와 짧은 진동을 실제 논리/이미지 이벤트에 동기화하고 연쇄가 많을 때 동시 재생 수를 제한한다. 광고/전화/백그라운드 전환 시 게임 음향을 일시 중단하고 복귀 후 사용자의 설정대로 복구한다.

18. R2 배포와 운영 도구

- 공개 런타임 에셋은 content hash/버전 경로와 적절한 캐시 헤더를 사용한다. 운영 제공은 custom domain을 사용하고 r2.dev를 운영 CDN으로 가정하지 않는다.
- 작은 manifest로 콘텐츠 버전을 확정한 뒤 해당 버전의 에셋을 로드한다. 실행 중인 판의 룰과 리소스를 중간에 교체하지 않는다.
- 앱 내 초반 필수 에셋 또는 검증된 로컬 캐시를 확보하고, 필수 리소스가 로드되지 않았는데 하트를 먼저 차감하지 않는다.
- CORS, 캐시, 네트워크 실패 재시도, 해시 검사, 이전 버전 fallback과 배포 rollback을 마련한다.
- 클라이언트에 R2 쓰기 권한이나 Cloudflare 관리 토큰을 넣지 않는다.
- 운영자 도구는 최소한 레벨 JSON/seed 미리보기, 생성 검증 결과, 경제 config, 이벤트 기간/보상, 장애물 해금, 계정/거래 조회를 제공한다. 일반 플레이어가 접근할 수 없도록 인증한다.
- 로그와 텔레메트리는 튜토리얼 완료, 레벨 시작/종료, 실패 이유, 하트 부족, 무제한 수령, 부스터 소비, 재접속, 구매 검증, 선택 광고 시작/실패/보상 확인/지급을 기록한다. 사용자 신원과 비밀값을 과도하게 수집하지 않는다.

19. 구현 진행과 완료 기준

작업 순서는 환경 점검/명세 파일화 → 결정론 엔진 → 초반 튜토리얼 → 핵심 이미지 기준 → 실제 이미지 UI → 하트·계정·저장 → 길드·경제·결제·선택형 광고 → 콘텐츠 생성/검증 → 모바일 빌드/시각 검수다. 병렬 작업이 가능하면 엔진·아트·서버를 분리하되 공통 계약과 asset manifest를 먼저 고정한다. 매 단계에 멈춰 허락을 구하지 말고 연결된 결과로 진행한다.

다음은 완료 기준이며 단순 TODO로 남기지 않는다.
- 게스트 첫 실행부터 1~5판, 홈, 정원 복원, 다음 판까지 실제 플레이 가능.
- 교환/특수 블록/모든 조합/장애물/낙하/승패/이어하기가 정의대로 동작.
- 반복 생성되는 후기 레벨과 멀리 떨어진 번호의 레벨도 정상 공급.
- 하트와 무료 4시간 보너스가 실제 서버 시각과 동시성 규칙으로 동작.
- 길드 2계정 이상의 하트·아이템 지원과 수령을 검증.
- Google·Apple 연동과 기존 계정 충돌 흐름을 구현. 실계정 검증에는 자격증명 상태를 정확히 표시.
- 상점·패스의 실제 데이터 흐름, 네이티브 결제 adapter와 서버 검증/중복 방지 구현.
- 하트 +1/클리어 코인 2배의 자발적 광고 시청, SSV 지연·중복·순서 역전, 시청 중 하트 상한 도달, 귀속 보상의 기부 차단을 검증. 광고를 보지 않았을 때 기존 보상과 진행이 보존되는지 확인.
- 모든 실제 화면에 최종 이미지 에셋이 연결되고 도형/깨진 이미지/이모지 placeholder가 남지 않음.
- 이미지 UI의 늘어짐, 잘린 코너, 비율 왜곡, 흐릿한 타일, 폰트 잘림을 수정.
- 시작/보상/지원/구매에 재시도와 중복 요청을 넣어 이중 차감·이중 지급이 없음을 확인.
- 같은 seed와 행동이 클라이언트/서버에서 동일 결과인지 의미 있는 fixture로 확인.
- 마지막 이동 승리, 겹친 특수 효과, 막힌 보드, 전체 목표 삭제, 무제한 종료 경계, 59분 회복 후 추가 소비, 선물함 최대치, 기기 시계 변경, 앱 백그라운드/재접속을 검증.
- 네트워크 실패/에셋 실패와 게임 패배를 구분하고 상태를 복구.
- 지원 화면 크기에서 홈/시작/플레이/성공/실패/하트/길드/상점 스크린샷과 주요 애니메이션을 직접 검수.
- 브라우저 검증, 시뮬레이터 빌드, 실제 기기 측정, 스토어 sandbox 결제 검증을 구분해 보고한다. 하지 않은 검증을 했다고 쓰지 않는다.

최종 산출물: 실행 가능한 저장소, 실제 사용 이미지 원본/최적화본/atlas와 manifest, 개별 생성 프롬프트, 레벨 데이터와 검증 도구, D1 migrations, Workers/R2 설정, .env.example, 테스트 결과, README, architecture.md, game-rules.md, economy.md, art-guide.md, 운영/배포 지침. 새 개발자가 README대로 로컬에서 켜고 필요한 외부 설정을 식별할 수 있어야 한다.

- 100%, 50%, 실제 게임 크기에서 실루엣과 모양이 읽히는가.
- 타일별 시각적 크기, 광원, 그림자, 바닥선이 일관적인가.
- 버튼 상태를 전환해도 크기와 pivot이 튀지 않는가.
- 9-slice에서 코너와 얇은 테두리가 찌그러지지 않는가. 리본 양끝이 늘어나지 않는가.
- 애니메이션 프레임 수, 재생 순서, 투명 마지막 프레임, 시작/끝 loop가 정확한가.
- 프레임 사이에 꼬리/날개/얼굴/파편 수가 의도 없이 변하지 않는가.
- atlas trim/padding/extrusion이 맞고 다른 타일의 색이 경계에 비치지 않는가.
- 원작 로고·캐릭터·정확한 UI 모양이나 생성된 글자가 섞이지 않았는가.
- 실제 게임 장면에서 보드가 배경/이펙트보다 먼저 읽히는가.
- 자동 검사와 실제 contact sheet/애니메이션 미리보기 결과를 남겼는가.

==================== 공식 참고 자료 ====================

이 프로젝트의 새 이름·세계관·경제 수치·4시간 무료 보너스·길드 아이템 지원·무한 생성 설계는 자체 제안이다. 아래 원작 사실과 혼동하지 않는다.

Royal Match 공식 확인:
- 본편은 목표와 이동 횟수가 있는 매치3이며, 별로 공간을 복원한다.
- 원작 생명은 실패 시 1개 소모하고 30분마다 1개 회복한다. 기본 상한은 5다. 이 문서의 매판 시작 시 차감/1시간 회복은 사용자 요청에 따른 별도 규칙이다.
- 원작은 코인·보물 패키지를 판매하며 코인을 추가 이동·생명·부스터에 사용한다.
- 원작 Royal Pass는 무료/유료 보상과 기간 제한이 있는 패스다. 독립 유료 저금통을 확인한 것으로 쓰지 않는다.
- 공식 Google Play 소개는 광고 없는 게임으로 설명한다. 이번 게임의 하트 충전·코인 2배 선택형 보상 광고는 사용자가 추가로 요청한 자체 정책이며 원작에서 확인한 기능으로 쓰지 않는다.
- 원작 공식 스토어는 신규 레벨 업데이트를 설명한다. 알고리즘으로 완전 무한 생성된다는 근거로 사용하지 않는다.
