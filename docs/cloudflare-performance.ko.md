## 클리어 화면과 저장

마지막 이동의 로컬 연출이 끝나면 클리어 모달을 표시한다. 행동 저장과 `/finish`는 뒤에서 진행한다. 확정 전에는 예상 보상과 확인 중 안내를 표시하고 다음 레벨·광고 보상 사용을 제한한다. 정원으로 돌아가는 것은 가능하다. 코인·별·레벨은 서버가 확정한 Player 응답으로만 변경한다.

`finishPending`을 행동 큐와 함께 저장하므로 마지막 행동 저장 후 큐가 비어도 보상 확정 작업이 사라지지 않는다. 재시도는 동일한 `finish-{runId}` 키를 사용한다. 앱 재시작 후에도 재시도하며, 홈에서 보상이 확정되면 홈에 머문다. 서버가 로컬 결과를 거부하면 해당 진행으로 다시 맞추고 잘못된 클리어 모달을 닫는다.

## D1 왕복 감소와 측정

- 플레이어·현재 시즌·검증된 시즌 클리어 점수를 한 SQL로 조회한다.
- `/me`의 플레이어와 활성 퍼즐도 같은 SQL에서 읽는다.
- 인증과 해당 세션의 요청 횟수 검사를 한 D1 배치로 처리한다. 만료·폐기된 세션은 횟수를 올리지 않는다.
- 중복 요청 기록과 플레이어를 같은 D1 배치에서 읽는다. 원장에는 이때 확보한 실제 저장 전 잔액을 사용하므로 플레이어를 다시 읽지 않는다. 추가 수신자는 한 번에 조회한다.
- 클리어 시 퍼즐·기존 보상 여부·전체 클리어 수·10판 보상 지급 기록을 함께 조회한다. 시즌 존재 여부는 앞서 읽은 스냅샷을 사용한다.
- 버전 조건, 퍼즐 시퀀스 조건, 고유 보상 제약, operations 기록, 원장과 보상 쓰기는 기존과 같이 원자적인 D1 배치로 커밋한다.

보상 확정의 기존 경로는 인증을 포함해 D1 왕복 13회였다(기존 코드 경로 기준). 현재 운영 응답의 `X-D1-Calls`는 4회다. 프로필은 2회다. `Server-Timing`의 `app`은 Worker 처리 시간, `db`는 대기한 D1 호출 시간 합계, `db_calls`는 SQL 문장 수가 아닌 D1 왕복 수다. 백그라운드 outbox 처리는 이 측정에서 제외했다. 쿼리·토큰·본문은 성능 로그에 기록하지 않는다.

## 운영 비교

같은 컴퓨터/연결에서 매번 새 임시 게스트로 승인된 레벨 1 행동을 재생했다. 보상 중복 요청과 하트 유지도 확인한 뒤 해당 임시 계정만 익명화했다. 실제 설치 계정·토큰은 사용하지 않았다.

단위: 밀리초, 전체 응답 시간의 중앙값.

| 요청 | 기존 (3회) | 조회 개선/배치 끔 (3회) | 조회 개선/Smart (5회) |
| --- | ---: | ---: | ---: |
| 프로필 | 1350.0 | 588.0 | 548.1 |
| 퍼즐 시작 | 1987.3 | 1312.4 | 811.9 |
| 행동 저장 | 2154.2 | 1545.3 | 813.7 |
| 보상 확정 | 2972.0 | 1155.2 | 831.1 |

Smart Placement 상태는 `SUCCESS`, D1의 보고 리전은 `APAC`이었다. 최종 측정 40개 요청에서 `cf-placement`는 `remote-HKG` 32개, `local-PDX` 8개였다. `CF-Ray`의 LAX/SEA 등은 요청 입구이며 실행 위치는 `cf-placement`로 구분한다. 따라서 모든 요청이 한국이나 DB와 같은 도시에 고정되었다는 뜻은 아니다.

홍콩에서 처리된 보상 확정 4건의 Worker 처리 시간은 219, 232, 233, 1338ms였다. 실제 전체 응답은 네트워크 경로·D1 지연의 영향을 계속 받는다. 측정 횟수가 적고 시간대와 입구 위치도 달라 엄밀한 A/B 실험이나 전 지역 성능 보장으로 해석할 수 없다. 로컬 렌더러는 네트워크를 기다리지 않으므로 이런 편차가 클리어 화면 시작을 막지는 않는다.
