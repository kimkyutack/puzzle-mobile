# 서버 배포·퍼즐 규칙·맵 데이터 분리

`ENGINE_VERSION`은 타일 계산 및 서버 재생 검증의 규칙 버전이다. Worker 버그 수정, 재화·이벤트 처리 변경, 호환 맵 추가 때문에 이 값을 올리지 않는다. Worker 배포 ID와 콘텐츠 발행 버전은 따로 관리한다.

## 버전 협상

- `/health.supportedEngineVersions`가 서버에서 유지하는 규칙 목록이다. 앱은 자신이 구현한 목록과 공통인 버전을 선택한다. 서버의 최신 버전이 앱보다 높다는 이유만으로 시작을 막지 않는다.
- `/health.engineVersion`은 기존 설치 앱을 위한 호환 필드로 `1.3.0`을 유지한다. 최신 규칙은 `latestEngineVersion`으로 별도 노출한다. 새 엔진을 추가할 때 이 호환 필드를 함께 올리지 않는다.
- `/runs/start`에 선택한 `engineVersion`과 앱의 `supportedEngineVersions`를 보낸다. 기존 단일 버전 요청과 버전 없는 예전 요청도 처리한다.
- 활성 판이 있으면 저장된 정의·시드·남은 횟수·규칙을 그대로 반환한다. 앱과 서버가 그 판의 규칙을 지원하지 않는 경우에만 업데이트를 요구한다. 서버에 새 규칙을 추가할 때 기존 규칙 구현과 지원 목록을 유지해야 한다.
- 기존 온실 기믹과 캠페인의 규칙은 `GARDEN_ENGINE_VERSION` 1.3.0에 고정했다. 서버 최신 규칙 상수를 바꿔도 기존 제작 함수가 새 번호로 정의를 다시 만들지 않으며, 벌크 정의의 규칙 번호도 임의로 덮어쓰지 않는다.
- 일일 구조 미니게임도 같은 고정 규칙을 사용한다. 서버 최신 규칙 번호가 바뀌어도 기존 클라이언트의 구조 행동 기록을 그대로 재생한다.
- 로켓 생성 방향 변경은 별도 규칙 `PERPENDICULAR_ROCKET_ENGINE_VERSION` 1.4.0부터 적용한다. 가로 4개는 세로 로켓, 세로 4개는 가로 로켓을 만든다. 1.0–1.3의 저장 판·카탈로그·승리 해시는 기존 방향을 유지한다. 2레벨의 안내 feature도 실제 생성되는 세로 로켓에 맞춘다. 기존 제작 카탈로그를 새 규칙으로 조회하는 경우 보드 정의는 복사하며 원본은 바꾸지 않는다.
- 앱 부팅은 건강 확인 결과에 묶이지 않는다. 홈·계정 로드는 별도로 진행하고 규칙 협상은 퍼즐 미리보기와 시작에 적용한다.
- 앱을 켜 둔 사이 지원 목록이 바뀌어 미리보기가 거절되면 목록을 한 번 갱신해 공통 규칙으로 다시 조회한다. 플레이 요청에는 이때 확인된 미리보기의 규칙을 사용하며, 재협상이 반복되거나 미리보기가 실패하면 판 생성·아이템 사용 요청을 보내지 않는다.

## 맵 데이터

인증된 `GET /levels/next?engineVersion=1.3.0`은 현재 계정의 다음 판을 반환한다. `{schemaVersion,contentVersion,level,levelHash}` 형식이며 판 생성이나 재화 사용은 하지 않는다. `levelHash`는 정의 JSON의 SHA-256이다.

실제 앱의 시작 모달은 이 정의의 목표·전략·레벨 번호를 표시한다. 앱에 포함된 `APPROVED_LEVEL_COUNT`로 새 레벨을 차단하지 않는다. 조회 실패 시 재시도와 홈 복귀를 제공한다. 내려받는 것은 JSON 데이터이며 실행 코드를 내려받지 않는다. 앱이 아는 규칙, 데이터 형식, 보드 크기·색상·장애물과 해시를 확인한다.

플레이 요청에는 사용자가 확인한 정의의 `levelHash`를 포함한다. 그 사이 맵이 바뀌었으면 서버는 부스터 사용·판 생성 전에 `CONTENT_CHANGED`를 반환한다. 앱은 자동으로 다른 맵을 구매하거나 시작하지 않고 새 목표를 불러와 다시 확인하게 한다. 이미 생성된 판은 저장된 정의를 계속 사용한다.

현재 요청의 성공 여부가 불분명한 네트워크 오류에는 시작을 자동 재구매하지 않는다. 같은 식별자와 부스터 선택으로 기존 중복 방지 처리를 유지한다. 미리보기 캐시는 세션 메모리에서만 사용하며 새로 모달을 열 때 다시 조회한다. 기존 서버에 새 조회 API가 없어 `NOT_FOUND`가 반환되는 경우에만 호환되는 앱 내장 정의를 사용한다.

## 앞으로 배포하는 방법

기존 규칙으로 만든 맵은 콘텐츠 제작·승인 검증을 마친 뒤 서버의 맵 카탈로그와 콘텐츠 발행 버전만 배포한다. 이 프로토콜을 포함한 앱은 새 정의를 조회하므로 그때마다 스토어에 올릴 필요가 없다. 기존 저장된 판의 정의와 규칙은 교체하지 않는다.

앱에 없는 타일 동작, 새로운 장애물·화면·그림이나 호환되지 않는 데이터 형식을 추가할 때는 앱 업데이트가 필요하다. 특히 현재 내장 맵만 읽는 구버전 앱이 이 다운로드 방식을 사용하려면 최초 한 번의 앱 업데이트가 필요하다.

이 변경은 로컬 코드와 검증까지 수행했다. 운영 Worker 배포, 네이티브 리소스 교체, 아카이브 및 스토어 업로드는 수행하지 않았다. API와 새 앱을 배포할 때 DB 마이그레이션이나 기존 판 초기화는 필요 없다.

## 검증

- 이번 후속 작업은 `tsc --noEmit`와 전체 56개 테스트 파일·369개 테스트를 통과했다. 앱이 켜진 도중의 규칙 재협상·확인한 규칙으로 시작·재시도 횟수 제한·미니게임 규칙 보존을 추가로 확인했다. 결과는 `output/verification/engine-content-no-build/`에 있다.
- 사용자 요청에 따라 이번 후속 작업에서는 웹·Worker·APK·iOS 빌드, 네이티브 동기화, 배포·스토어 업로드와 Git 푸시를 수행하지 않았다. 기존 설치본과 운영 서버에 이 코드가 반영됐다는 의미는 아니다.
- 사전 준비 작업에서는 웹 프로덕션 빌드와 `tools/api-engine-content-http.ts`의 실제 로컬 Worker·임시 D1 검증을 수행했다. 건강 확인 호환 필드, 인증·읽기 전용 미리보기, 미래 버전 서버와의 공통 규칙 선택, 맵 해시 및 무차감, 기존 판 유지, 10,001레벨의 다운로드·재생·중복 정산 방지를 확인한 과거 기록이다. 이 도구는 내부적으로 Worker 번들을 만들기 때문에 이번 빌드 금지 요청에서는 재실행하지 않았다.
- `tests/client-remote-levels.test.ts`: 내장 카탈로그 이후의 맵, 중복 다운로드 공유·명시적 갱신, 구 서버만의 내장 맵 폴백, 손상·미지원 데이터 거절과 변경된 목표의 재확인을 검증한다.
- `tests/engine-rules-stability.test.ts`: 서버 최신 엔진이 미래 버전으로 바뀐 상황에서도 기존 1.3.0 캠페인·복합 기믹의 승리 기록과 상태 해시가 일치하는지 검증한다.

사전 준비 작업의 로그와 HTTP 결과는 로컬 `output/verification/engine-content/`에 보관한다. 다른 채팅의 정원 카메라·이펙트 변경과 네이티브 빌드는 이 작업에서 수정하거나 교체하지 않았다.
