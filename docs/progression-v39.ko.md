# 칸별 장애물과 양 끝 타격 자석 레일

사용자 영상의 맵은 큰 그림 하나에 내구도를 채워 구역 전체를 여는 장치가 아니었다. v37의 큰 차양·2×2 저장함 위주 새 맵을 독립된 상자 칸으로 바꾸고, 별도의 긴 자석 레일을 함께 도입했다.

## 규칙과 배치

- 상자 구역: 상자마다 독립 ID와 한 칸짜리 footprint를 가진다. 맞은 상자만 한 겹 손상되거나 없어지고 주변 상자는 남는다. 보강된 일부 상자는 2겹이다.
- 자석 레일: 한 칸 너비의 연속 경로다. 양 끝 자석 옆에서 자연 매치를 만들거나 끝을 직접 타격하면 맞은 쪽 한 칸만 열린다. 몸통 옆 매치나 몸통 직접 타격은 먼 끝으로 피해를 전달하지 않는다.
- 한 효과는 같은 레일을 한 칸만 줄인다. 연쇄 매치나 여러 벌의 독립된 타격은 각 효과마다 한 칸씩 줄일 수 있다. 양 끝이 동시에 맞으면 경로의 앞 끝을 우선한다.
- 몸통에 망치를 사용하려는 입력은 `PIPE_END_REQUIRED`로 거부한다. 상태와 이동 횟수, 아이템 수량을 변경하지 않는다. 유도형 특수 타일은 몸통 대신 노출된 끝을 목표로 고른다.
- 열린 칸은 일반 보드 공간이 되어 타일이 내려온다. 물길 스테이지의 열린 바닥과는 별도 규칙이다.

| 구간 | 구성 |
|---|---|
| 1~30 | 기존 학습 구간 유지 |
| 31~100 | v37에서 승인한 63개 일반 판의 목표·이동 예산 조정 유지 |
| 101~200 | 한 줄 상자로 개별 칸 열기 학습, 일부 판에는 길이 3의 짧은 레일. 예: 104는 상자, 114는 상자+레일 |
| 201~400 | 굽은 상자 배치와 서리, 일부 판에 길이 5 레일. 예: 214 |
| 401~700 | 여러 상자 구역·덩굴·서리, 일부 판에 길이 7의 꺾인 레일. 예: 414 |
| 701 이후 | 어려움·매우 어려움 판에서 복합 상자와 최대 길이 14의 굽은 레일. 예: 718 |

레일은 모든 맵에 강제로 넣지 않는다. 짝수 변형은 칸별 상자 중심을 유지하고, 일부 홀수 변형에 레일을 섞는다. 쉬운 판과 스토리 스테이지는 복잡한 레일로 바꾸지 않는다. 원래 카탈로그에 있던 큰 색상 차양도 새 판에서는 승인된 칸별 장애물 템플릿으로 바꾼다.

## 앱과 서버 호환

자석의 끝만 판정하는 새 규칙은 엔진 `1.9.0`과 콘텐츠 `garden-2026.11.06-progression-v39`에만 적용한다. 기존 `pipe`에 `endOnly: true`를 명시하며 이 필드를 지원하지 않는 엔진에는 해당 정의를 보내지 않는다.

기존 1.8 앱에는 `garden-2026.11.06-progression-v38`의 독립된 한 칸 상자 맵을 제공한다. 1.0~1.7 앱의 공개 카탈로그와, 이미 시작한 모든 판의 `Run.level` 및 저장 상태는 유지한다. 1.8의 기존 물관은 종전처럼 옆이나 몸통 타격으로 앞에서 줄어드는 규칙을 보존한다. 최신 앱도 이 저장 판을 호환 규칙으로 이어간다.

API는 승인된 JSON과 해시만 읽으며 요청 중 맵 탐색·제작을 수행하지 않는다. 새로운 게임 규칙은 앱의 로컬 엔진에도 필요하므로 자석 레일은 동기화된 앱 리소스로 새 Archive를 만든 뒤 사용할 수 있다. 이후 같은 규칙 안의 배치·목표·이동 예산 조정은 맵 데이터 배포로 처리한다.

## 리소스와 검증

끝 자석·직선 연결부·모서리 3개 PNG를 내장 `image_gen`으로 각각 제작했다. 한 이미지를 큰 영역으로 늘리지 않고 경로의 각 칸에서 원본 비율로 회전·연결한다. 큰 내구도 숫자는 레일 위에 표시하지 않는다. 원본은 `packages/assets/source/magnet_rail_*_v39.png`, 전체 프롬프트와 출처는 `packages/assets/magnet-rail-v39-prompts.json`이다.

- 새 배치 47개와 초기 조정 63개: 110개 승리 기록을 실제 로컬 엔진으로 재생했다. 초기 자동 매치·선택지 부족·강제 섞기가 있는 후보는 승인하지 않는다.
- 기존 1.8용 110개 맵의 이전 승리 해시도 별도로 보존하고 재검증했다.
- 자연 매치의 양쪽 끝 판정, 몸통 무반응, 행 경계, 굽은 경로, 한 효과당 한 칸 축소, 마지막 칸 수거, 빈 칸 리필, 유도 타겟 및 구버전 규칙을 검사했다.
- 전체 테스트 71개 파일 / 492개 테스트, TypeScript, 운영 Worker dry-run 통과.
- iOS·Android의 운영 API 설정 리소스 536개가 웹 빌드와 해시 일치. iOS Release API 검사 통과. iOS 1.06(7), Android 1.05(6)을 유지했으며 Archive/스토어 업로드는 하지 않았다.

작성된 배치에 구매 없는 해법이 있다는 검증이며, 무작위 재도전 전체의 성공률이나 사람의 체감 난이도 검증은 아니다. 증거는 `output/verification/progression-v39/`에 보관한다. 운영 배포·HTTP 결과는 `deploy.log`와 `production.json`을 기준으로 확인한다.

## 운영 반영 완료

- Worker `puzzle-mobile`: `86701370-5426-45ca-b88b-171056c7c407`을 배포했다. 기존 환경 변수·바인딩·스케줄을 유지했으며 DB 스키마 변경은 없다.
- 운영 31/104/114/204/214/231/404/414/708/718레벨의 다운로드·시작·로컬/서버 상태 일치·클리어·중복 시작/보상 방지 검사가 통과했다. 1.8은 독립 칸 맵, 1.7은 기존 카탈로그를 받는 것도 확인했다.
- 첫 검사에서 배포 전 만들어 둔 v37/1.8 판이 그대로 이어지고 클리어하는 것을 확인했다. 중간 요청 한 건이 30초 지연되어 그 임시 계정을 정리한 뒤 새 QA 계정으로 운영 검사를 재실행했고 전체 통과했다. 두 계정 모두 정리했다. 두 번째 준비 판은 배포 후 생성한 것으로, 원래 배포 전 판 보존 증거는 `production-first-attempt.json`과 `before-deployment-original.json`이다.
- iOS·Android 리소스 동기화와 Release API 검사는 완료했다. 버전 번호 유지, Archive·스토어 업로드·Git 커밋/푸시는 실행하지 않았다.
