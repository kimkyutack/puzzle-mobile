# 연속 복원과 이야기 v30

복원에서 지역을 선택하던 탭과 홈의 `정원 꾸미기` 아래 `6/6` 표시를 제거했다. 복원 화면에는 전체 순서의 다음 작업 하나만 나온다. 이야기 기록도 지역 탭 없이 시간순 목록 하나로 표시한다. 지역 ID는 그림·지도 위치를 연결하는 내부 정보로만 남는다.

기존 18개 작업의 ID, 가격, 순서, 완료 기록을 유지하고 45개 작업을 뒤에 추가했다. 기존 초대장 이야기에서 배달하지 못한 편지를 따라 우체국, 반딧불 연못, 숲속 역으로 이어진다. 총 63개 복원과 프롤로그를 포함한 64개 이야기다. 새 작업은 159별, 기존 포함 193별이다. 기본 별 획득만 고려하면 최소 193회 클리어 분량이다. 새 구간마다 15개 작업을 마치면 기존과 같은 100코인 보너스를 한 번 준다.

기존 건물의 이동·회전·보관 상태는 유지된다. 새 시설도 안정된 인스턴스 ID로 한 번만 지급한다. 기본 위치를 다른 시설이 차지한 경우 복원 보상은 보관함으로 지급하고 안내한다. 새 지도 구역은 해당 순서의 첫 작업 복원으로 열리며, 다른 작업의 유료 20칸 확장과 구분된다.

## 대기 개선

- 누르는 즉시 반투명 시설 미리보기와 망치 연출을 시작한다. 미리보기는 로컬 표현이며 실제 별·소유권은 서버 결과로만 갱신한다.
- 서버 저장과 연출을 겹치고 최소 준비 600ms 뒤 공개한다. 응답 후 남는 공개 연출은 350ms다. 실패하면 미리보기를 걷고 기존 정원 상태를 유지한다.
- 복원 API는 별 차감·시설 저장을 같은 트랜잭션으로 처리하고 갱신된 Player와 world를 함께 반환한다. 이를 사용하므로 복원 뒤 world GET을 추가하지 않는다. 오래된 캐시 응답에 world가 없는 경우에만 재조회한다.
- 이야기 마치기는 기기 저장소에 계정별 감상 대기열을 기록하고 즉시 닫는다. HTTP 저장은 백그라운드에서 진행하고, 실패하면 재접속·10초 재시도로 다시 보낸다. 64장면은 기존 서버와 호환되는 최대 19개씩 전송한다. 저장소 자체가 실패하면 오류를 보여준다.
- 새로 연 이야기는 확정된 Player에서 로컬로 계산한다. 복원마다 story GET을 반복하지 않는다. 서버 감상 처리는 이미 읽은 Player를 재사용하고 기록·외형·일일 구조 조회를 D1 batch로 묶는다.
- 정원 결과는 ownerId와 revision을 확인해 오래 도착한 응답이 최신 배치를 덮지 않도록 한다.

## 이미지

우체국·우편함·버드나무·나루·기차역·객차는 새 전면·후면 이미지 12개, 선로는 지면 이미지 1개다. 기존과 동일하게 앞/뒤의 좌우 동반 방향으로 4방향을 지원한다. 이야기 장면 3개도 새로 제작했다.

원본과 정확한 프롬프트:

- `packages/garden-world/art/story-v30-prompts.json`
- `packages/assets/story-v30-prompts.json`
- `node --import tsx tools/garden-world/build-story-v30.ts`
- `npm run assets`

## 검증과 배포 범위

`tools/api-story-v30-http.ts`는 임시 D1에 새 검증 계정만 만든다. 기존 18개 완료, 새 45개 순차 복원, 저장된 world 일치, 별·보너스·중복 요청·동시 요청·이동한 시설 보존·64개 감상 저장을 실제 Worker HTTP로 검증한다. `--ui`는 localhost:5198에서 390×844 화면을 띄우며 복원 응답을 3초, 감상 응답을 8초 늦춘다. 실제 앱에서는 두 응답을 기다리지 않고 각각 미리보기/창 닫기가 먼저 일어나는 것을 확인한다. 감상 기기 저장 재시도는 별도의 outbox 테스트로 확인한다.

전체 53개 테스트 파일의 343개 테스트와 TypeScript 검사, Vite 빌드가 통과했다.

브라우저 검증에서 복원 미리보기는 클릭 후 약 0.3초, 이야기 닫기는 약 0.3초에 나타났다. 이는 의도적으로 지연한 로컬 검증 결과이며 운영 서버 RTT 측정 결과는 아니다.

운영 Worker 배포와 네이티브 설치 파일 교체는 이 작업에서 수행하지 않았다. 기존 서버는 새 복원 ID를 알지 못하므로 실제 사용자에게는 서버와 새 클라이언트를 함께 배포해야 한다. 별도 작업 중인 엔진·정원 확장·일일 구조 변경도 같은 체크아웃에 있으므로 전체 배포 범위를 확인해야 한다. 기존 데이터 재설정이나 DB 마이그레이션은 필요 없다.
